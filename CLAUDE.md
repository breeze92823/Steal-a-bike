## Current state: the lobby
The lobby is built (from the reference screenshots of the original game: north, south, west and east views): a lego plaza walled in by purple terraces, an east-west road, the bike plots south of the road, the shops north of it, and the SAFE ZONE lane north through 12 zones, one per Bike Index world in order (1-4 hand-built from the user's screenshots: Plain World grass, Lake raised grass, Desert sand, Snow + ice gate; 5-12 generated: Jungle, Swamp, Candy, Crystal, Magma, Cosmic, Aurora Nexus, Angel Biome), each guarded by a sleeping police vehicle from the screenshots; only Magma, Cosmic and Aurora Nexus are dark, with procedural sound and per-zone lighting moods. The HUD is in place with live timers, ticking cash, the spawn announcement banner and Ride My Bike (rides your bicycle, faster, outside the safe zone only); the other buttons only toast "coming soon". Stealing works (`heist.js`): take a bike from a guard post, the guard wakes and chases you with siren and lights, escape over the SAFE ZONE line or get knocked off. Progress is saved on the server and other players are drawn (see Networking below). The old boat-racing code is in git `HEAD` (`git show HEAD:src/<file>`); check there before rewriting something generic (windows shell, net, audio).

Three.js (vanilla, no React) + Vite + Rapier (`@dimforge/rapier3d-compat`, wasm inlined; `main.js` awaits its init at top level, hence `build.target: 'es2022'`). Everything is procedural (canvas textures); the only imported model is the Bloxity base rig `public/avatars/player.glb`. Font: Fredoka (loaded in `index.html`).

- `npm run dev` / `npm run build`. `VITE_DEV_MODE=true` (see `.env.example`) skips the Bloxity SDK/CDN. Deploy: `.github/workflows/deploy.yml` uploads `dist/` to Bloxity Hosting (main = prod, dev = dev channel).
- All tunables are in `src/config.js` (the rest of `src/` holds no theme values). It now has: identity (`GAME_SLUG`, `GAME_TITLE`, `DEV_MODE`), the lobby (`LAYOUT`, `LANE` (zones 1-4: north edge, floor height, guard post, sign amount; the ice gate), `MOODS` + `ZONE_THEMES` (worlds 5-12: name = INDEX_WORLDS name, `rec`, `guard` {kind, mk, name}, `dark`, looks), `ZONE_GEN`, `AUDIO`, `RIDE`, `HEIST` (steal prompt reach, guard wake/chase speed per tier, knockdown, respawn, siren), `TRAINING`, `PALETTE`, `TIMERS`, `ANNOUNCE`, `HUD_START`, `SLOW_MODE_SCALE`, `SPAWN`, `SPAWN_FACING`), `MODES`, `PHYSICS`, `PLAYER_DIMS`, the look (`RENDER`, `FOG`, `TIME_OF_DAY`, `LIGHT`, `CHARACTER_COLORS`, `MATERIAL_PBR`, `GRAPHICS_PRESETS`, `BLOOM`, `NEON`, `graphicsPreset`), `TOUCH`, `CAMERA`, `SETTINGS`, and the rig (`RIG*`, `PROPORTIONS`, `ANIM`).

## Bases (plots.js, base.js)
- Every plot is a player's base. The game server gives each player in the room one (roster `plot`; a room holds 7 players = 7 plots); offline you get `LAYOUT.myPlot`. `plots.js` draws all seven: yours from your own state (`base.js` + `training.level`), everyone else's from the roster (`floors`, `placed`, `treadmill`, sent with `net.sendBase` whenever `base.version` or the treadmill level changes), "Unclaimed" when nobody has it. Each plot: the Club Tourer, the parked bikes slot by slot, floor by floor (`BASE.floors`), their tags (others' only within `BASE.detailRange`), the owner's name, on yours a rising "+$N" per bike; on others' plots the two signs show their treadmill level and floors. Rebuilt only when that base changes (baked: one mesh per material for decks, one for bikes).
- Floors: the ground (5 slots + the Club Tourer) and up to two steel decks (`BASE.deck` apart, 12 slots each) on pillars, with ramps outside the plot (west up to deck 1, east up to deck 2, `BASE.ramp`). Decks, pillars and ramps have colliders (`physics.removeCollider` takes them away when the base changes). The Upgrade Base sign at the plot's north-west corner shows a button (tap or E, empty-handed) that buys the next floor for `BASE.floors[n].price`. `floors` is saved.
- When your plot changes, `main.js` `onMine` moves `base.setPlot`, `training.setMill` (your treadmill is that plot's), and `SPAWN.x` (R / falls bring you home), and teleports you there if you are still near spawn.

## Networking (Bloxity multiplayer, saves, leaderboard)
- `net.js`: Colyseus client to the backend room `world`. Deployed builds resolve a pod through the matchmaker (`bloxity.resolveServerEndpoint`, a new Client per endpoint, retry with backoff, re-resolve when the room closes); `npm run dev` uses `SERVER_URL` (ws://localhost:2567, `VITE_SERVER_URL_DEV`). Joins a `?roomId=` invite/party room first (`locateRoom`), reports the room with `updateRoom` so friend invites land in it, and tells Bloxity who is in the room (`playerJoined` / `playerInRoom`). The join sends the Bloxity game token (`getToken`) so a deployed server verifies the id. Guests are never saved.
- Saving: every module that has state calls `registerStore({ snapshot, hydrate })` from `stores.js` (hud cash/speed/income are handled in net.js via `hud.restore`). On `progress` each hydrate runs; the whole snapshot goes out as `saveProgress` at most every `NET.saveEvery` s when something besides ticking cash changed (and at least every 30 s, and when the tab hides). Stores: sellshop (`bikes`), trailshop, bikeindex, training (`treadmill`), fuse, daily, base (`placed`). New saved state: register a store + add the field to the backend `sanitize.ts` / `db.ts`.
- Presence: `main.js` sends `sendPose` (10 Hz, only when it changed), `sendLoadout` (trail, held bike) and `syncAvatar()` (Bloxity look JSON incl. skin texture, on avatar/proportion changes); `remotePlayers.js` draws the nearest `NET.maxRemotes` others (avatar via the same loader as yours, riding / walking-a-bike states, name tag, dead reckoning).
- MOST CASH board (`market.js`): the server's global top 50 by cash, `LEADERBOARD.rows` per page, paging every `LEADERBOARD.pageEvery` s, "Your rank" at the bottom; "Server offline" when not connected. Bloxity's own trophy boards (`LEADERBOARDS` in config.js: Most Cash, Top Speed) are declared in `bloxity.js` and reported by the server; Bloxity draws the trophy button. `BLOXITY_CODE_METADATA.md` records `hasScore: true, canDie: false`.
- FREE GIFT! (`gift.js`, `GIFT` in config): the chest in the hub uses the stall prompt (`createPrompt` with `alt`, no window): hold E (or the prompt on touch) on its disc to watch a Bloxity rewarded ad (`bloxity.showRewarded`, only while `canShowRewarded()`), the server verifies the ad token (`net.claimAdReward`), then +100 Speed and a 5-minute cooldown (the prompt counts down; the server clock decides). VITE_DEV_MODE has no SDK: it pays at once so it can be tried locally. `BLOXITY_CODE_METADATA.md` says `rewards: true`.
- Other Bloxity features (after Lumber-empire): chat bubbles (`bloxity.onChat` -> `bubble.js`, over your head and, by the roster `uid`, over others'), emotes (`bloxity.onEmote` -> `avatar/emotes.js` + the animator's `playEmote`; relayed with `sendEmote` and played on remotes from the roster `emote`), ad breaks (`onAdBreak`: the loop freezes, `audio.setAdBreak` silences, `releaseInput`), portal cursor lock (`onPointerLock`), Gems helpers (`buyGems`, `net.onGems`; the server owns the balance), screen ads (`showScreenAd` / `hideScreenAd`, not used yet). The game slug is `steal-a-bike` (`GAME_SLUG`).

## Mobile & responsive (required for every change)
The game must play on phones and tablets (portrait and landscape) as well as desktop. Treat a feature as unfinished until it works on touch and on a small screen.
- **Input**: every action needs a touch path, not just a key. Use Pointer Events (`pointerdown/move/up`, check `e.pointerType`), never mouse-only events. Layout (implemented in `src/touch.js`): left-thumb virtual joystick -> `inputState.move`, right-side drag -> `inputState.look`, on-screen buttons for jump/sprint/mode/etc., pinch -> `inputState.zoom`. Everything still feeds `inputState` in `src/input.js` so game code stays input-agnostic. Pointer lock does not exist on touch; never rely on it.
- **Detection**: decide touch UI with `matchMedia('(pointer: coarse)')` / `navigator.maxTouchPoints`, not the user agent. Show touch controls only on coarse pointers; a device can have both.
- **Layout/UI**: HUD and menus use relative units (`%`, `vw/vh`, `dvh`, `clamp()`) and flexbox/grid, no fixed pixel layouts. Tap targets >= 44px. Respect notches with `env(safe-area-inset-*)` (viewport already has `viewport-fit=cover`). Text readable at 360px width. No hover-only interactions. Add `touch-action: none` on the canvas and game controls so the browser does not scroll/zoom.
- **Resize/orientation**: anything sized to the screen (camera aspect, renderer, HUD) must react to `resize` (covers orientation changes). Use `visualViewport` where the on-screen keyboard or browser bars matter.
- **Performance**: mobile GPUs are weak. Respect the `graphics_quality` presets in `src/config.js` (cap DPR, shadow map size, draw distance); default to a lower preset on coarse-pointer devices. Avoid per-frame allocations; keep draw calls and texture sizes low.
- **Testing**: check every UI/input change at a phone viewport (e.g. 375x812 and landscape 812x375) with touch emulation, plus desktop, before calling it done.
